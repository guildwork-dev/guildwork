# 07 Eval

Source keys and classifications as in the [README](README.md). The eval decides what goes live, not the feature wish. The thresholds per service (Gate A, Gate B) are stated only in [10](10-standards-per-layer.md); this file defines **with what** and **how** measurements are taken. Background and raw figures are in the research documents under `docs/research/` (dated, not binding).

## 1. Eval infrastructure

- **One harness for all services and all providers.** An eval run is a normal platform run with `effect_sink: record`: the same chain of router, policy, ledger, Work API, worker, sandbox, and Effect Gateway, except that the effects land in the eval log instead of at the provider. SCM and ticket responses come from fixtures. This measures exactly what runs live.
- **Two-part eval (ADR-52):**
  - **Public eval package in the product repo** (folder `eval/`): adapters, download scripts, own labels, reference tables with dates. Third-party benchmarks are **never stored there as a copy**, but as a script with a pinned commit or dataset revision and a checksum; the script downloads at runtime. Reason: the benchmark repos are MIT, Apache-2.0, or CC-BY-4.0, but the PRs they contain are code of the source repos under their licenses ([`ebene-review`](../research/ebene-review.md) section 7 item B). Own public sets consist of references (repo, commit, path, lines, issue number) and own labels under the project license.
  - **Private sets per installation** in the same format, stored at the operator (private repo or object storage of the installation). They are never published and do not feed into the reference qualification.
  - **Data path of private sets (ADR-70):** A private case inherits the repo class and `data_policy` of its source repo (`source_ref`). The eval runner starts a case only through a runtime that would also be permitted for this repo in operation (data path, provider allowlist, conditions of the credential kind); an eval run is not a way around the policy. For `subscription` this means: every source repo is listed in `operator_repos` of the runtime ([05](05-security.md) section 6 condition 10). Otherwise the runner rejects the case before the start, with an audit entry and the reason in the eval report.
- **Shared adapters:** (a) the **ReviewBench container contract** for all review sets (repo at head under `/work/repo`, diff, output `findings.json` with `file`, `start_line`, `end_line`, `message`; [rb-contract] VERIFIED); the same adapter serves R2, R4, R5, and own review sets. (b) the **Harbor format** for coding, QA, and terminal tasks (public image as `SandboxSpec.image`, the task's checker in a fresh sandbox, "locked protocol" as with Scale; [harbor] VERIFIED, [scale-lb] VERIFIED).
- **Case metadata** per case: `set`, `case_id`, base SHA, snapshot digest, input, expected result, `license` (SPDX), `source_ref` (repo and commit), `labeler`, and `origin` with exactly one value from `public_benchmark | own_public | human_labeled | private_installation | vendor_output`.
- **Block on `vendor_output`:** Cases whose ground truth comes from outputs of a third-party product (CodeRabbit comments, SonarQube findings) are rejected by the eval runner by default. Reason: the CodeRabbit terms of use ([12](12-open-source-and-project.md) section 5.3) prohibit in 4.2 (iv) "use the Services to develop competing products or services without CodeRabbit's prior written consent" and the disclosure of benchmark results; [sonar-aup] §5 and §6 contain corresponding clauses (a reading of the texts, not legal advice; references in [`gegenpruefung-lizenz-und-recht`](../research/gegenpruefung-lizenz-und-recht.md)). For the project the block is permanent (O18, O19 decided: not connected, no request); such cases are never published.
- **License rule for datasets (ADR-50 by analogy):** The standard run uses only sets with a verified free license. Copyleft data (such as OWASP Benchmark, GPL-2.0) is only loaded at runtime, never stored in the repo. Noncommercial data (such as TestGenEval, CC BY-NC 4.0, [testgeneval] VERIFIED) only as an explicitly enabled optional download, never in the standard run. Sets without a license statement (such as SWE-RPG) are not used; only their method is rebuilt on own data.
- **Results** per qualification profile (section 2, ADR-66) in `eval_runs`, stored with `qualification_key` and the complete profile, with cost and duration per case, date, and state of the reference (leaderboard version). A stored result is valid only as long as reference and combination are unchanged; if either changes, it expires.
- **Execution** on a pool of the installation with its own pool limit (for the project's reference runs: pool `self-hosted` with `single_operator: true` of the project, because the project runs only through the subscription, O28; services with a shell on public sets according to ADR-72; without a budget cap according to O22, throughput is limited by the usage limits of the subscription). Limits are measured before and after every eval run; exceeding them aborts hard (suite S3).
- **Judges:** For public benchmarks their own judges apply so that values are comparable (Martian: profile `core`, F-beta 2, scored under all three judges of the file, Claude Opus 4.5, Claude Sonnet 4.5, and GPT-5.2, and the one least favorable to the candidate counts; ReviewBench: Claude Sonnet 5; [mcr-method], [mcr-repo], [rb-readme] VERIFIED; rule in [10](10-standards-per-layer.md) section 1.5). For own sets an LLM judge with a fixed prompt and a pinned version, if possible a different model than the candidate (`judge-alt` in [04](04-configuration-and-limits.md)); in the project this is a different Claude model, not a different vendor (O28), and the same model family is noted in the report. **Deviation of the project (O28):** The project scores R2 Martian only under the Claude judges of the file (Claude Opus 4.5, Claude Sonnet 4.5), not under GPT-5.2; its R2 values are therefore not directly comparable with the leaderboard, and the report states this. If benchmark judges run through the subscription, the pinned benchmark code calls the model through `claude-cli` (ADR-73). Calibrated against a sample with human labels; the agreement between judge and human is reported per set and measured again at least every quarter. A change of judge is itself a change with a regression run.

### 1.1 Statistics

- Every value is reported with a 95% interval, every difference likewise, as a cluster bootstrap over PRs or tasks. Gate A and Gate B are **one-sided non-inferiority tests** with a margin, minimum power, and the outcome "not decidable"; the rule and the margins are stated only in [10](10-standards-per-layer.md) section 1.4 (ADR-56).
- **Goal "resolve 10 points"** means: the half-width of the 95% interval of a difference is at most 10 percentage points (N15). Calculation (DERIVED, normal approximation, p = 0.5):
  - independent proportions: n = 1.96² × 2 × 0.25 / 0.1² ≈ **192 cases per arm**;
  - **paired evaluation** (the same cases with and without the platform, McNemar): the variance depends on the share of discordant pairs. With at most 25% discordant pairs, **about 100 cases** suffice (1.96 × sqrt(0.25/100) ≈ 9.8 points). The share of discordant pairs is an estimate and is measured after the first run;
  - anyone who wants to **detect** a true difference of 10 points with 80% power needs about 392 cases per arm independently or about 196 paired at 25% discordant pairs (z = 1.96 + 0.84). The same number applies to the minimum power of a non-inferiority test with a margin of 10 points (Gate A); with a margin of 5 points (Gate B) it is about 1,570 cases per arm independently or about 790 paired (2.8² × 0.25 / 0.05², DERIVED).
- **Consequence:** Gate A is always evaluated paired (same cases, same model, bare harness against platform). Own sets have a starting size of 100 cases (estimate); whether a set decides is governed by the minimum power ([10](10-standards-per-layer.md) section 1.4), and a not decidable Gate A is decided by a larger own set. Individual public sets are often smaller than the goal (R2: 158 golden comments in profile `core` on 50 PRs, cluster bootstrap for F2 about ±8.7 points, own recalculation 2026-10-31; HARD-51: at 90% about ±8 points; [`ebene-coding`](../research/ebene-coding.md) 3.3). Therefore Gate B evaluates a basket of several sets per service, never a single small set.

## 2. Qualification matrix, modes, and gates

- **Qualification profile (ADR-66):** A row of the matrix is determined by the `qualification_key`, the hash of a canonical qualification profile. It contains: `service`, harness with version, `credential_kind`, provider, the runtime's model and **all** `models.*` per role (such as `gate`, `finder`, `verifier`, `gate_model`, `notes_model`), `prompt_v` **per stage** of the service, the plugin versions, and all config keys that are marked as quality-relevant in the JSON Schema (`x-qualification: true`, such as router thresholds, filters, profile, `max_comments`; [04](04-configuration-and-limits.md) section 7). Canonical means: keys sorted, references to ModelProvider resolved to provider and model, default values written out. **Library calls** of other services (such as the reviewer in the coder's self-review, the architect's plan conformance in the reviewer, the QA library "E2E smoke" in the coder; [02](02-services.md)) inherit the profile of the calling service: their model and their `prompt_v` are in the caller's profile and are qualified with it, never through the row of the called service. The config snapshot of every run stores the profile and `qualification_key` per participating service ([04](04-configuration-and-limits.md) section 1 rule 5); the policy compares only the hash, not individual fields. A profile without a measured row is not qualified, even if it differs from a qualified row only in a gate or verifier model.
- A row (one `qualification_key`) is **qualified** when Gate A, the required parts of Gate B, and the required suites S1 to S6 are green (ADR-28, ADR-47, [10](10-standards-per-layer.md) section 1.2). S8 applies per installation and release, not per row.
- **`live` requires Gate A and Gate B (ADR-47).** There is no longer a qualification with "Gate B open" (N2): a row without green required parts is not qualified; the reference qualification lists it with its Gate B status ("red", "not decidable", or "open"), and its expansion stage is nevertheless done as soon as it is built, the suites and Gate A are green, and Gate B is measured and reported (rule in [10](10-standards-per-layer.md) section 1.2 item 6, ADR-55). Alternative path: an **adopted reference qualification** (section 2.1). Without either, the service runs at most `shadow`. Only the operator may deviate, via the installation configuration; the row then visibly carries the label **"standard not proven"** in the admin UI, status comment, and check text, and the audit records the deviation. Where [10](10-standards-per-layer.md) does not yet name a measurable Gate B reference for a service, `live` is therefore only possible with this label.
- `merge.mode: auto` and the automatic plan approval additionally require a green suite S7 for the installation and the combination used.
- **Shadow mode** provides online data without external effect: the effects land in the eval log, and a human can view and rate them in the admin UI. Costs count against the limits.
- **Regression gate:** Every change to prompt, filter, threshold, model, harness version, plugin version, or judge runs against the regression subset of the sets before rollout. A degradation beyond the interval blocks the rollout.
- **Fallback providers** are only permitted if they are qualified for the service themselves.

### 2.1 Reference qualification (ADR-52)

- The project measures the reference combinations on the public sets for each release and publishes the qualification matrix including logs, costs, and reference states in the release (results from private sets never).
- An installation may **adopt** a published row under the conditions of [10](10-standards-per-layer.md) section 1.2 item 2: same platform release and same qualification profile (section 2, ADR-66), that is, also all `models.*` per role, `prompt_v` per stage, plugin versions, and marked config keys. The credential kind may differ within the same provider (the profile is then compared without the field `credential_kind`) until the contract test in stage 1 confirms or refutes this; a different provider path (such as Bedrock instead of the Claude API with the same model) counts as a different combination.
- **Remeasurement in shadow mode:** After the adoption, the installation re-measures Gate A in shadow on its private set; if it fails, the policy automatically sets the service back to `shadow` ([10](10-standards-per-layer.md) section 1.2). In addition, shadow mode continuously measures the service's online metric; if, after at least 50 human-rated results (starting value, estimate), it is significantly (95%) below the published reference value, the adoption expires as well.
- **Not adoptable** are the installation-dependent suites S1 to S8 (permissions, limits, isolation, failure paths, autonomy, installation): they always run on the installation itself, against fixtures and without LLM costs where possible.
- If the project changes the reference (new leaderboard version) or the installation changes the combination, the adopted row expires.

### 3.4 Coder

1. Pull merged PRs that close an issue and change tests.

### 3.9 Triage

**T1 own public set** from public repos with active maintenance: issues that maintainers closed and linked as duplicates (ground truth: the link), labels and assignees that maintainers set. **T2:** spam and slop from contributions hidden or blocked by maintainers plus planted cases. The eval package contains only references (repo, issue number, point in time) and own labels; the script downloads the texts. Starting size 100 duplicate pairs and 100 non-duplicates (estimate). Private parts per installation optional.

**Metrics:** Duplicate precision and recall with citation, label agreement, spam and slop detection, **0 automatic closings without approval** (O25: closing only as a repo opt-in after a green T1 of this repo). **Online:** label adoption rate, suggestions reverted by maintainers. There is no public benchmark for triage ([`ebenen-landkarte`](../research/ebenen-landkarte.md) section 5 item 4); Gate B therefore measures T1 against the workflow "Issue Triage" of gh-aw, re-measured ourselves, as a required part only once the license of gh-aw is VERIFIED ([10](10-standards-per-layer.md) section 12). A comparison with CodeRabbit Issue Enrichment is dropped (O18).
