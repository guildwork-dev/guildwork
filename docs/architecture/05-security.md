# 05 Security

Source keys and classifications as in the [README](README.md). Principle: the boundary is the separation of privileges, not the model. No model, no prompt and no filter has to decide "correctly" for nothing bad to happen.

This file describes the rules of every installation. What a particular installation has decided (base, credential choice, network, org state) is in the private ops repo of this installation (ADR-38), not here.

## 1. Trust zones

| Zone | Content | holds |
|---|---|---|
| Z0 control plane | ingress, router, policy, ledger, Work API, platform MCP, Effect Gateway, Credential Broker, Postgres, BlobStore | GitHub App keys, OIDC signing keys, plugin secrets, all via the `SecretStore` driver (section 5) |
| Z1 worker host | worker binary, container runtime, egress proxy with credential relay | only the revocable pool key (may only `claim`, `heartbeat`, `complete`, `fail`, `uploadUrl`) or the OIDC token of the CI system in the CI dispatch job (GitHub Actions, GitLab CI; [06](06-operations-and-deployment.md) section 2a); per item the LLM credential in the memory of the relay (WIF access token or key from the broker, discarded with the item); with a subscription additionally the operator's subscription token (section 6) |
| Z2 sandbox | agent, repo code, build, tests, analyzers | no long-lived secrets; setup secrets are removed before the agent phase; of the LLM credential only a placeholder, the real one is inserted by the credential relay in Z1 (section 3). Exceptions, each with a condition: short-lived cloud credentials of an item role for `bedrock`, `vertex`, `foundry` until the relay contract test; the subscription token for `subscription` only in services without a shell and without write access to files, except profile `operator_test` (section 6, condition 9). Platform MCP token bound to exactly this work item |
| Z3 outside world | SCM, tickets, LLM providers, identity providers | |

**Z0 and Z1 on one host (`single-host`, ADR-62):** the topology puts the worker and the control plane on the same host ([06](06-operations-and-deployment.md) section 2). The zone boundary only holds there if all points apply:
- The worker never talks to the Docker daemon of the control plane and never gets its socket. It runs under its own user with its own rootless daemon or behind a socket proxy that only allows creating, starting, stopping and removing containers and checks at creation: runtime from the verified isolation level (`sysbox-runc` or `runsc`), only the sandbox network of the item, no host paths (only named volumes per item), no `privileged`, no additional capabilities, no host network and no host PID namespace. Whether Sysbox runs with a rootless daemon is unverified; therefore the socket proxy is the default of the Compose bundle and rootless the alternative after a contract test (stage 0).
- The worker container is not attached to the network of Postgres, SeaweedFS and the control plane and sees neither `secrets/` nor `.env`; it reaches the Work API and platform MCP like an external worker via the reverse proxy.
- Every sandbox is only attached to an internal network without egress (`internal: true`), whose only way out is the egress proxy (as in [06](06-operations-and-deployment.md) section 2a). Sandbox networks never touch the Compose network.
- `doctor` checks every point ([11](11-installation-and-hosting.md) section 2.2); a case in S6 tries to reach `secrets/`, Postgres and the Docker socket of the control plane from the worker and the sandbox (gate: 0 successes).

**Residual risk `single-host`** (DERIVED): kernel and host are shared. An escape from the sandbox up to root on the host reaches `secrets/` (app keys, OIDC signing keys), Postgres and a subscription token. For repos of the class `external_code` (section 3) and for multi-user operation, the documentation therefore recommends the worker pool on a second VM (worker package, [11](11-installation-and-hosting.md) section 2.7).

## 2. Separation of privileges

1. **The agent has no write credential to the outside.** No SCM write token, no ticket token in Z2. It only writes to the workspace and expresses write requests via the platform MCP.
2. **The platform MCP runs in Z0**, not as a sidecar in the sandbox. The agent reaches it via HTTPS with an item token: valid only for one work item, only its repos, only the read tools and `propose_*` tools that the service may have according to [02](02-services.md) section 0, lifetime at most until the end of the lease. The pool key is never accessible to the agent (process separation in the worker, file not mounted into the sandbox). This way a compromised agent can neither claim items nor forge other write requests.
3. **Effect only if the command covers it:** the policy derives allowed effects from the triggering command and the pipeline stage. A review job cannot produce a push, no matter what the model proposes. Authorization never comes from tool output or model text (ADR-06).
4. **The Effect Gateway** executes write requests deterministically: idempotency key per effect, `expectedOldSha` on push, no force, only `agent/*` branches (in the repo or in the agent fork of the installation, ADR-59; never a human PR branch, ADR-71; the only exception is the fixed anchor branch of the daily anchor with profile `audit_anchor`, section 8), bundle check (paths, secrets, size), fallback chains per capability, secret redaction and removal of external links and images from comments (against Markdown exfiltration), quotes and references checked against the visibility of the target (section 7, ADR-63).
5. **Approve only for human PRs; merge only through the merge gate:** the SCM contract has `approve` only as an optional method for human PRs (O24, ADR-14): SHA-bound, only via the Effect Gateway, only with `services.reviewer.auto_approve: true` and the conditions (a) to (d) from ADR-61 ([04](04-configuration-and-limits.md) section 3), never for agent PRs; the platform withdraws its approve on every new push. Auto-merge additionally requires the provenance condition (merge gate condition 12) and is blocked for repos of the class `external_code` (ADR-60). `merge` is an optional method that only the Effect Gateway with the permission profile `merge` may call, and only after the deterministic merge gate with `merge.mode: auto` ([03](03-flow-and-orchestration.md) section 1a, ADR-36). No service can request a merge (no `propose_merge`); model text or tool output cannot satisfy the gate, because it only checks stored facts at the SHA. The GitHub App never has `workflows`, `administration` or bypass permissions; the hoster's branch protection also applies to the platform's merge. With `merge.mode: human` and `shadow`, the required status `agent-approval-check` (SHA-bound) prevents any merge without a human approve. Tests: permission test against the real app and suite S7.
   **Open (unverified, stage 5):** whether "required approve for human PRs" and "merge without approve for agent PRs after the merge gate" can be combined in one repo on GitHub without bypass permissions or a bot approve. Ruling: bypass and bot approve on agent PRs remain forbidden (the optional approve of human PRs under O24 is separate from this, point 5 above). If it does not work without one of the two, the repo stays on `merge.mode: human`, or its branch protection requires no approve but the required checks including `agent-approval-check`. The repo owner decides this. In the second case three obligations apply, otherwise the repo stays on `human`:
   - `agent-approval-check` is bound to the platform's app as its source.
   - Push to `agent/*` is only allowed for the app.
   - The platform sets the check on human PRs only after a human approve at the SHA.

   In addition, the merge gate requires that all commits come from the Effect Gateway ([03](03-flow-and-orchestration.md) section 1a, condition 11).

**Permission profiles per effect** (the Credential Broker mints the token per effect, one repo, short-lived). The setup wizard creates the GitHub App via the manifest flow with exactly these permissions (ADR-45, [11](11-installation-and-hosting.md)):

| Profile | Effects | GitHub App permissions | Ticket permissions |
|---|---|---|---|
| `read` | clone before agent start by the worker, discarded afterwards | `contents:read`, `pull_requests:read`, `issues:read`, `checks:read`, `actions:read` (CI logs) | read |
| `review` | review, check, summary, thread reply; approve of a human PR only with `auto_approve` (O24, agent PR term in [01](01-plugin-interfaces.md) section 5) | `contents:read`, `pull_requests:write`, `checks:write` | none |
| `comment_issue` | plan and status comment, transition, remote link | `issues:write` | comment, transition, link |
| `labels` | `propose_labels`, `propose_link`, `propose_issue` (triage, reviewer with `summary.labels: apply`, PR fixer in the `ci_doctor` mode) | `issues:write`; labels on PRs additionally `pull_requests:write` | labels, links, create issue |
| `rerun` | `propose_rerun` of the PR fixer: restart failed jobs of the current SHA, at most once per commit | own checks via `checks:write`; workflow jobs would need `actions:write`, which the main app never has. There the fallback level is a notice to humans (DERIVED; which permissions the rerun needs on GitHub is unverified, contract test in stage 4) | none |
| `write_branch` | push to `agent/*` (in the repo or in the agent fork, ADR-59), open a draft PR and set it to ready | `contents:write`, `pull_requests:write` | remote link |
| `audit_anchor` | daily anchor of the audit chain as a commit on a fixed branch (default `guildwork-audit-anchor`, never `agent/*`, never the default branch) in the repo from `audit_anchor.repo` (section 8) | `contents:write`, only this one repo | none |
| `merge` | merge of an agent PR at the verified SHA (`sha` parameter, [gh-merge] VERIFIED), only after the merge gate | `contents:write`, `pull_requests:write`, only for this one repo, minted only for this one effect | transition `done` |
| `dispatch` | start a job in the runner repo of a CI dispatch pool (`workflow_dispatch`, [06](06-operations-and-deployment.md) section 2a) | `actions:write`, only via a **separate dispatch app** that is installed exclusively on the runner repo | none |
| never | | `workflows`, `administration`, bypass, approve on agent PRs; `actions:write` in the main app | admin, project configuration |

Reason for the separate dispatch app (DERIVED): an app permission applies to all repos on which the app is installed. The token can be restricted to repos per request ([gh-insttoken] VERIFIED), but an error in the broker could then mint `actions:write` for a product repo. With `actions:write`, workflows with its secrets could be started there. The dispatch app cannot do that, because it is not installed on any product repo.

GitHub installation tokens expire after 1 h and can be restricted to repos and permissions per request ([gh-insttoken] VERIFIED). GitLab has no short-lived, restricted token: project access token per repo with minimal role, up to 365 days, on GitLab.com only from Premium ([gl-pat] VERIFIED); the platform encapsulates it in the broker, rotates it by calendar and marks the installation in the admin UI with "SCOPED_SHORT_TOKEN missing".

## 3. Sandbox

- **A fresh container or a fresh microVM per work item.** `destroy()` always, also in the failure path (test).
- **Isolation (ADR-48):** three levels that the `ExecutionBackend` offers ([01](01-plugin-interfaces.md) section 8):
  - `sysbox`: root in the container mapped to an unprivileged host uid, Docker-in-Docker without `--privileged`, kernel shared ([sysbox] VERIFIED). Risk: Docker sponsors Sysbox, but it is "not officially supported by Docker", support "best effort" ([`hosting-und-installation`](../research/hosting-und-installation.md) section 2.8, VERIFIED).
  - `gvisor`: kernel in userspace, platform `systrap` runs without virtualization on any Linux VM ([gvisor-plat] VERIFIED). Equivalent to `sysbox` for own code; Docker-in-Docker inside it unverified, therefore for QA with E2E only after a contract test.
  - `microvm`: Firecracker (E2B self-hosted) or Kata; needs `/dev/kvm` ([e2b], [`hosting-und-installation`](../research/hosting-und-installation.md) section 2.8, VERIFIED).
- **Minimum isolation per repo class** (DERIVED, enforced when routing to pools):

  | Class | When | Services that execute repo code (coder, QA, PR fixer, verifier with build, analyzers with `runsRepoCode`) | Services without execution of repo code (reviewer without build, planner, architect, triage, docs without build) |
  |---|---|---|---|
  | `private_own` | repo private at the hoster, trigger and all authors of the diff have write permission | at least `sysbox` or `gvisor` | `sysbox` or `gvisor` |
  | `external_code` | everything else: repo public, fork PR, author without write permission, third-party code (customers, contributions) | only `microvm` | `sysbox` or `gvisor` |

  The orchestrator determines the class on every claim from fresh provider data (visibility, fork, permissions of the authors), not from the configuration alone. A pool only gets an item if its **verified** capabilities match: the worker reports at `claim` what it actually found (`/dev/kvm` readable and writable, `sysbox-runc` or `runsc` registered, RuntimeClass present), not what is configured. Reason: some environments look like normal Linux hosts but cannot do KVM or privileged containers ([`hosting-und-installation`](../research/hosting-und-installation.md) section 2.8). If a matching pool is missing, the item stays put with reason `no_qualified_pool` (status `neutral` "no suitable pool", [03](03-flow-and-orchestration.md) section 5); it never falls back to a weaker level. Key: `isolation_min` in [04](04-configuration-and-limits.md) section 7, profiles per base in [11](11-installation-and-hosting.md) section 3. Test in S6.
- **Consequence for the project's own public repo** (DERIVED): the development repo is public, hence `external_code`. Until the microVM backend (stage 9), only services without execution of repo code run there: on fork PRs the reviewer without build, on issues triage without a shell, each in the mode `shadow` or `live` depending on qualification. Coder, QA, PR fixer and the verifier with build only run there from stage 9, because the default branch of a public repo also contains merged third-party contributions. Via the subscription, only runs that the operator triggers themselves, and only services without a shell, run there (section 6, conditions 3 and 9); runs triggered by other people need an API key or WIF. The project uses only the subscription (O28); third-party contributions therefore get no platform run on the own repo. Merges there are done only by humans: the resolver rejects `merge.mode: auto` for `external_code` (ADR-60).
- **Two phases** (Codex pattern [codex-cloud] VERIFIED): setup with secrets and open network, after which secrets are removed; agent phase without secrets and only with an egress allowlist.
- **Egress proxy** with an allowlist per service: reviewer, planner, architect, triage and docs only the LLM endpoint and the control plane (the reviewer only needs the registry if the verifier builds); coder, QA and PR fixer additionally registry caches. Every connection is logged.
- **Registry cache and DNS without a back channel (ADR-64):** in the agent phase, the registry cache serves offline only artifacts that were loaded in the setup phase from the repo's lockfile; it answers a request for a different name or a different version with "not present" and never resolves upstream. The agent reports a new dependency as the write request `propose_dependency` (ecosystem, name, version); the worker loads it into the cache outside the sandbox, only if the name is in the repo's name allowlist (`security.dependencies.allow`, [04](04-configuration-and-limits.md)) and the osv check is green, otherwise the request becomes a question to a human. The sandbox has no DNS resolver; names are only resolved by the egress proxy, and only for hosts on its allowlist. Reason: a pull-through cache carries data to the outside via package or module names, and DNS queries via arbitrary names (for Go modules the mechanism is known, for this setup unverified). Cases in S1.
- **File permissions:** `.git` read-only for the agent, `.git/config` and credential files not readable (`denyReadPaths`). The clone is done before agent start by the worker via ASKPASS with a `read` token, which is discarded afterwards; token never in the URL.
- **LLM credential separated from the agent phase:** the agent reads untrusted content (repo code, PR and ticket texts of other people) and has `edit+shell` as coder; everything in its environment counts as readable. Therefore:
  1. **Credential relay:** Claude Code (and Codex) only talk to the relay in the egress proxy (`ANTHROPIC_BASE_URL` or `ANTHROPIC_BEDROCK_BASE_URL`, pinned via managed settings with `allowedProviders: ["customEndpoint"]`, [cc-auth], [cc-gateway], [cc-bedrock] VERIFIED). The sandbox only contains a placeholder per item; the relay checks item binding, target host and path and only sets the real header (`X-Api-Key` or `Authorization: Bearer`) when forwarding. Start path per credential kind: [01](01-plugin-interfaces.md) section 6. Anthropic describes the pattern (credential stays server-side, clients only hold a substitute) for LLM gateways ([cc-gateway] VERIFIED); the implementation in our own proxy is DERIVED and is proven by a contract test.
     **Limitation of the relay** (the placeholder is usable by the agent in services with a shell, so the relay may only do what the harness needs): path allowlist only `POST /v1/messages` and `POST /v1/messages/count_tokens`, everything else rejected; a body filter rejects requests with `mcp_servers` and with server tools (`web_fetch_*`, `web_search_*`, `code_execution_*` and other server tool types), because the Messages API reaches third-party hosts through them, bypassing the egress allowlist (MCP connector docs and web fetch docs, VERIFIED according to follow-up review 2026-10-31); `anthropic-beta` only from an allowlist; model allowlist per service and an upper bound for `max_tokens`. The relay reads `usage` from every response, books it against the item's reservation in the limit ledger ([04](04-configuration-and-limits.md)) and blocks the item when the budget is exhausted; in addition a rate limit per item. This way, direct calls bypassing the `claude` process also count. Fallback layer: switch off web search and web fetch for the workspace in the Console (effect unverified). Tests: [07](07-eval.md) S1 and S2.
  2. **Subscription exception:** the subscription token cannot go through the relay, because the platform would then "intermediate[s]" it ([cc-legal] VERIFIED, assessment DERIVED). It is therefore placed as `CLAUDE_CODE_OAUTH_TOKEN` in the environment of the `claude` process of the sandbox (start path ADR-57) and is only admissible for services with `nativeTools: none` or `read` (reviewer with `verifier.build: false`, planner, architect, `ask`); coder, QA, PR fixer and verifier with build do not run with `subscription` (resolver check at load time, [04](04-configuration-and-limits.md) section 3). The only exception is the profile `operator_test` (section 6, condition 9). In addition, `denyReadPaths` for `/proc/**`, the config directory and `.credentials.json`.
  3. **Cloud federation exception during the transition:** STS or federation credentials of an item role that may only make the model call on the allowed profiles, lifetime at most the lease; the target is the relay ([01](01-plugin-interfaces.md) section 6).
  4. **Redaction with own rules** for `sk-ant-oat`, `sk-ant-api`, AWS keys and the placeholder per item, in addition to the gitleaks default rules (whether gitleaks recognizes `sk-ant-oat` out of the box: unverified, hence an own rule). Applied in the Effect Gateway (comments, write requests), in the bundle check, before every storage in the BlobStore and in the OTel collector. A hit blocks the effect and creates an audit entry.
  5. **Repo content blocked as instruction:** `--setting-sources user` (no project settings, no `env` block of the repo, no `.mcp.json`), `--strict-mcp-config` with only the platform MCP, `disableAllHooks` via `--settings`; skills and agents of the repo are not loaded by `--bare`, without `--bare` they are blocked by `--setting-sources user` ([cc-headless], [cc-permissions] VERIFIED; effect on skills and agents without `--bare` unverified, contract test). **Base SHA rule also for agent files (ADR-17):** `CLAUDE.md`, `AGENTS.md` and `REVIEW.md` only apply in the version from the base SHA. The worker injects this version via `--append-system-prompt-file`. Whether Claude Code loads a `CLAUDE.md` from the workspace despite `--setting-sources user` is unverified; therefore a case in S1 checks that a `CLAUDE.md` changed in the head does not become an instruction. If the case fails, the worker replaces the head version in the workspace with the base version before agent start and passes the head version on only as `Untrusted` diff content.
  6. **Test in S1:** per credential kind, the agent tries to exfiltrate the LLM credential via `env`, `/proc`, file search, comment, write request and bundle. Gate: 0 hits of a real credential outside the relay ([07](07-eval.md)).
- **Repo configuration does not execute code outside the sandbox:** linter, analyzer and build configuration from the PR only run in the sandbox. Lesson from the remote code execution at CodeRabbit via a linter configuration in the PR ([kudelski-cr] CLAIMED). Analyzer rules and configuration come from the base SHA (ADR-17, ADR-40). Claude Code runs with `--bare` or its own `CLAUDE_CONFIG_DIR` plus a managed settings deny, because `-p` otherwise executes the repo's hooks and `.mcp.json` ([cc-headless] VERIFIED). Codex with repo configuration `untrusted` ([pullfrog] VERIFIED).
- **Claude Code sandbox** only in addition, with `failIfUnavailable`, never as the boundary ([cc-sandbox] VERIFIED).
- **Fork PRs:** only the reviewer without build until stage 9 (see minimum isolation), never coder or PR fixer on the fork branch; no `pull_request_target` with a checkout of PR code (DERIVED; GitHub warns that running untrusted code under `pull_request_target` can lead to security vulnerabilities, [gh-events] VERIFIED).
- **CI on agent branches like fork code (ADR-59):** the protection layers above only apply in the sandbox. The hoster's CI runs on every push of the Effect Gateway with the agent's code, including tests and build scripts it wrote; `forbidden_paths` only block workflow files. An app installation token lets `pull_request` workflows run without approval (GitHub docs "Triggering a workflow", read according to the Red Team on the overall idea, finding 4, not retrieved again here). Therefore coder, QA and PR fixer only run in a repo if one of two variants applies:
  1. **`agent_fork` (preferred):** the Effect Gateway pushes `agent/*` into a separate agent fork repo of the installation, to which only the app may write, and opens PRs from there. The hoster then treats the workflows as with fork PRs: no repo secrets, approval before the run according to the repo's fork setting (reference project: Copilot PRs only run after "Approve and run workflows", [`ebene-pr-fix-und-ci`](../research/ebene-pr-fix-und-ci.md) section 2.2, VERIFIED). Whether GitHub keeps this the same way for PRs from a fork in the same org, opened by an app, is unverified (contract test in stage 2).
  2. **`guarded_workflows` (installation prerequisite):** every job that uses a secret other than the `GITHUB_TOKEN` only runs in an environment with a required reviewer, or its workflow excludes `agent/**` per event (for `pull_request`, branch filters act on the target branch, so there only via a job condition on the head branch, detailed design 10 FE-1040; anything unknown counts as unprotected); no `pull_request_target` with a checkout of the head.

  `doctor` checks the variant per repo, the orchestrator again on every claim of coder, QA and PR fixer against the workflow files at the base SHA; the result is in the Run Record. Without evidence, the item stays put with reason `no_safe_ci` ([03](03-flow-and-orchestration.md) section 5). **Residual risk** (DERIVED): with `guarded_workflows`, jobs without secrets still run with the runner's open network; repo code can leak through it. Whoever must rule this out takes `agent_fork` with approval before every run. Case in S1.

## 4. Prompt injection

1. **Everything except the triggering command is data.** Ticket, PR text, code, comments, CI logs, ticket fields, KB content, issue text for triage, imported Learnings, guidelines in third-party formats (only read from the base SHA) and SARIF messages of third-party analyzers enter the prompt as `Untrusted<T>` (the type enforces the marking, [01](01-plugin-interfaces.md) section 1.1).
2. **Sanitizer** removes zero-width characters, bidi control characters, hidden HTML comments.
3. **TOCTOU:** if content is edited after the trigger, it is excluded and a question is asked.
4. **Structured output** enforces the schema; free text never ends up unchecked in an effect.
5. **Injection detector** (small model, from stage 9): only a signal that escalates a run to "approval required"; the boundary remains the separation of privileges.
6. **Eval requirement:** suite S1 with injection cases per input kind (issue text, code comment, CI log, commit message, KB content, ticket field, SARIF message, head version of `CLAUDE.md`). Gate: 0 effects outside the command, 0 exfiltration via network or comment ([07](07-eval.md)).

## 5. Secrets

- **The Credential Broker** in Z0 alone holds: GitHub App keys (main app and dispatch app), ticket service accounts, cloud federation configuration, OIDC signing keys, static provider keys (only where no federation is possible). It reads and writes them via the `SecretStore` driver (ADR-41; implementations `file`, `env` read-only, `azure-keyvault`; later `aws-secretsmanager`, `gcp-secretmanager`, `openbao`; contract in [01](01-plugin-interfaces.md)). The OIDC signing key is signed by a `SecretStore` with the capability `SIGN` in the KMS; without this capability it is stored as an encrypted file. OpenBao is a fork of Vault under the Linux Foundation ([openbao] VERIFIED; license MPL-2.0 according to the FAQ, license file unverified). Human secrets stay in the operator's password manager.
- **LLM without static keys:** Claude API via Workload Identity Federation through the `CloudIdentity` driver (`self-issuer`: the control plane is its own OIDC issuer and uploads its JWKS inline; `azure-managed-identity`; later AWS, GCP, projected Kubernetes tokens). Tokens 60 to 86,400 s; the lifetime is set by the federation rule, per item it is only limited by the `exp` of the broker JWT ([an-wif] VERIFIED, [01](01-plugin-interfaces.md) section 6). The exchange is done by the worker in Z1, the access token is held only by the credential relay, because `claude --bare` reads no federation variables ([cc-auth] VERIFIED; start path [01](01-plugin-interfaces.md) section 6). Pitfall: a set `ANTHROPIC_API_KEY` silently overrides WIF ([an-wif] VERIFIED); the worker therefore builds the harness environment empty plus the allowlist of the chosen credential kind ([01](01-plugin-interfaces.md) section 6). Bedrock, Vertex, Foundry via the federation of the respective cloud (details unverified, check before stage 8).
- **CI dispatch jobs** authenticate to the Work API via the OIDC of the CI system; with GitHub Actions the Work API checks `runner_environment`, `repository` and `job_workflow_ref` ([gh-oidc] VERIFIED). Platform credentials are never CI secrets: anyone with write permission on the runner repo could read them via their own workflow (DERIVED).
- **Prerequisite in the GitHub org:** the org default for `GITHUB_TOKEN` is set to read before the first agent run starts. `doctor` checks this, as far as the app may read it ([11](11-installation-and-hosting.md)).
- **Redaction:** gitleaks rules plus own rules for LLM credentials (section 3) before every effect, before every storage in the BlobStore and in the OTel collector. Code and secrets never in logs. Claude Code redacts telemetry content by default ([cc-monitoring] VERIFIED).

**Platform rule (ADR-51):** the credential kinds `subscription` (Claude) and `chatgpt` (Codex with ChatGPT login, [codex-auth]) are only a personal operator mode. They are blocked by default. Switching them on requires `acknowledge_terms` in the configuration with the version and date of the terms read ([04](04-configuration-and-limits.md)). The platform never implements a login, stores no token and passes none on beyond the worker host. The operator generates the token on their worker host themselves in the unmodified CLI (`claude setup-token`); the worker binary reads it there from a file that only the worker user can read and passes it locally to the `claude` process (ADR-57). The control plane never sees it. Whether this passing on counts as "intermediate" in the sense of [cc-legal] is open; it is an operator risk that the admin UI shows alongside `acknowledge_terms` (condition 8). For any autonomous operation, the documentation recommends an API key from the Console (including the capped plan credit), WIF or a cloud provider; the switch is a configuration change. Which credential kind an installation uses is decided by its operator. The project itself uses only `subscription` for development, eval, reference qualification and dogfooding (owner decision O28, residual risk with the Owner); the recommendation remains the default for third-party installations. For `chatgpt`, conditions 1 to 8 below apply analogously with harness `codex` and its unmodified CLI; there is no profile like `operator_test` for it, so only services without a shell ([01](01-plugin-interfaces.md) section 6).

**Conditions for credential kind `subscription`** (enforced, each with a check and a test):
1. Only harness `claude-code`, unmodified binary, pinned version with checksum (ADR-39). All conditions also apply to single calls via the ModelProvider `claude-cli` ([01](01-plugin-interfaces.md) section 7, ADR-58).
2. Only pool `self-hosted` with `single_operator: true`; one operator per pool, their own subscription.
3. **Trigger exclusively the operator themselves** (`allowed_triggers: operator_only`). No run triggered by another user runs via the subscription, not even with "approval" by the operator. Test in suite S2: a trigger other than the operator never leads to a subscription run.
4. The token lies only on the operator's worker host, generated with `claude setup-token` and stored in a file that only the worker user can read; never in the control plane, never in the DB, never in a snapshot or log, never as a CI secret, never transmitted over the network except in the model call to the LLM endpoint. `/login` is not a start path, not even with `max_concurrency` above 1 (ADR-57). The worker binary passes the token through locally, only as `CLAUDE_CODE_OAUTH_TOKEN` into the environment of the `claude` process; the control plane never sees it. Test in S1 and S2: no table, no log, no snapshot, no work item envelope contains an OAuth token (secret scan on fixtures and after a real run). In the sandbox it lies in the `claude` process; therefore only services without a shell and without file write permission (exception profile `operator_test`, condition 9), `denyReadPaths` and redaction according to section 3, test in S1.
5. No `--bare` (reads no OAuth [cc-auth] VERIFIED); own empty config directory, managed settings, `--setting-sources user`, `--strict-mcp-config` with only the platform MCP, `disableAllHooks`; this blocks hooks, `.mcp.json`, project `env`, skills and agents of the repo. Because without `--bare` agent files of the workspace can also load, the base SHA rule from section 3 point 5 explicitly applies here: `CLAUDE.md` and the other agent files only from the base SHA via `--append-system-prompt-file`, case in S1.
6. Limits only reactive (`rate_limit_event`); the ledger counts runs and tokens without USD.
7. Expiry of the token after one year ([cc-auth] VERIFIED) is monitored via `health()`.
8. The admin UI labels the option as "operator risk, not for multi-user operation", shows the version from `acknowledge_terms` and names the open risk that the local passing on of the token by the worker binary may count as "intermediate" (ADR-57).
9. **Profile `operator_test` (services with a shell on the subscription):** admissible for coder, QA, PR fixer and verifier with build, only if all points apply (resolver check at load time, test in S2):
   - Conditions 1 to 8 apply.
   - The repo is in `operator_repos` and is private at the hoster. The resolver checks this at load time, the orchestrator **again on every claim** via the SCMProvider; the result is in the Run Record. If the repo has meanwhile become public or is not readable, the run ends before agent start with `blocked` and an audit entry. Test in S2.
   - Trigger **and** ticket author are the operator. Thus ticket text and repo content come from the operator themselves, so there are no third-party inputs.
   - Egress only control plane, LLM endpoint and registry cache, no open internet.
   - **Inspection proxy for the LLM endpoint:** without a relay, the agent could use the token directly and reach third-party hosts bypassing the egress allowlist via server tools (`web_fetch_*`, `web_search_*`, `code_execution_*`) or `mcp_servers` of the Messages API (section 3 point 1). Therefore the egress proxy on the operator's worker host inspects the traffic to the LLM endpoint via TLS termination (own CA only in the trust store of the sandbox) with the same path and body filters as the relay. It forwards the auth header unchanged and does not store, log or replace it. Whether this counts as "intermediate" in the sense of [cc-legal] is a legal question that the operator assesses for their installation; without an inspection proxy, `operator_test` is blocked.
   - The token comes from `claude setup-token` and, according to Anthropic, can only make model requests ([cc-auth] VERIFIED).

   **Residual risk** (DERIVED): an agent with a shell can read the token. It can get out via three paths:
   - Control plane: comments, bundles and stored artifacts are redacted by point 4 in section 3.
   - LLM endpoint: the server tools are blocked by the inspection proxy. What remains is the model call itself, which only sends text to Anthropic.
   - Registry cache: offline, only artifacts from the lockfile, without upstream fetching; DNS is only resolved by the egress proxy (section 3, ADR-64).

   With `operator_test`, an agent only gets third-party instructions via third-party code in dependencies and tests, not via tickets. A leak of the token would be an abuse of the subscription quota; it ends with the revocation of the token, which itself has no permissions on code or accounts.

   Gates in S1: 0 hits of the token outside the LLM endpoint, and a test host that the agent tries to address via `web_fetch` or `mcp_servers` with the subscription token receives 0 requests.
10. **Eval runs on the subscription (ADR-70):** the eval runner uses a runtime with `subscription` only for public sets and for private cases whose source repo is in `operator_repos` of this runtime. Private sets from other repos (for example of an organization or an employer) never run via the subscription, but only via a runtime that the `data_policy` of their source repo allows ([07](07-eval.md) section 1). Test in S2: 0 runs. **Operator eval with a shell (ADR-72):** an eval case run on a public set (`effect_sink: record`, only fixture SCM without write methods, started by the operator) may execute services with a shell in the profile `operator_test`; it only replaces the points "repo in `operator_repos` and private" and "trigger and ticket author are the operator" from condition 9, all other points apply. Test in S2: a case run with a write method or with a trigger other than the operator yields 0 subscription runs.

For multi-user and org operation, Claude Code (also on own hardware in the pool `self-hosted`) with an API key or WIF, Bedrock, Foundry, Vertex and the other harnesses are available; the choice is made by the operator of the installation.

## 7. Tenants and identity

- `tenant_id` (installation and org) in every table, row-level security in Postgres; every query sets the tenant from the auth context.
- Item token, worker key and platform MCP are limited to the tenant, the work item and its repos.
- Knowledge base: namespace per repo; cross-repo search only within one tenant and only with `CROSS_REPO` approval in the org configuration. Learnings are not pooled across tenants (reference project Copilot Memory, not pooled across repos [copilot-memory] VERIFIED).
- **Visibility rule across repo boundaries (ADR-63):** a run only reads sources that anyone who can see the output target is allowed to see; the target therefore reaches at most as far as the visibility of each source. Order `public` before `internal` before `private`: a public target (comment, issue, PR in a public repo) only gets public sources; sources of another private repo only with `CROSS_REPO` and only for a private target. This applies to the KnowledgeStore, issues and PRs, code, Learnings (as in [02](02-services.md) section 7) and `related[]` of the reviewer, and to triage, reviewer, indexer (`ask`) and every later service. The orchestrator reads the visibility freshly from the provider at claim, not from the configuration. The Effect Gateway additionally checks every quote and every reference (repo, path, issue or PR number) of an effect against the visibility of the target and otherwise blocks with an audit entry. Case in S1.
- **Developer MCP** (stage 6, [02](02-services.md) section 4a): token per user, permission check at the provider on every call, only read tools; the only write request is "marked as fixed", which the next incremental run verifies.
- Identity linking (ticket account to SCM login) only via OAuth confirmation by the user themselves (`identity_links`), never via email equality alone.
- **Admin UI sign-in IdP-neutral:** a generic OIDC client (authorization code with PKCE); every OIDC provider is configuration (issuer URL, client ID, client secret in the `SecretStore`), not a plugin. Roles `viewer`, `approver`, `admin` come from a configurable group claim with a mapping table; without a matching group there is no access. The roles are read anew from the token at every sign-in, not stored.
- **Emergency admin:** at first start, the installer CLI creates a local admin with a one-time password (output only on the console, change and TOTP at the first sign-in). It serves for setting up the IdP and for IdP outages. Every sign-in of the emergency admin creates an audit entry and an alert; the CLI can lock and reset it.
- Only the Work API, ingress and platform MCP must be publicly reachable; the admin UI may be, only behind OIDC.

## 8. Audit

- **Append-only table** `audit(seq, prev_hash, hash, tenant, actor, action, subject, details_ref, at)`, hash-chained.
- **Daily anchor:** a job writes the end-of-day hash into a sink outside the database, so that a later change becomes visible (ADR-29). Two sinks: a `BlobStore` with the capability `OBJECT_LOCK` (immutable for the retention period) or a commit via the SCMProvider into a repo named by the operator. Without a sink the chain continues, `doctor` reports an error and the admin UI shows "audit anchor missing". The `fs` driver has no Object Lock; on `single-host` the repo sink is therefore the default.
- **Run Record per run:** trigger event (hash and raw reference), resolved permissions, config hash, prompt and plugin versions, harness version with checksum, model and provider, image digest, isolation according to the verified capability, repo class at claim, CI variant at claim (ADR-59), attribute `foreign_input_seen` with source and author of every `Untrusted` input from people without write permission or after the trigger (ADR-60), all tool calls (name and argument hash), policy decisions with rule ID, approvals (who, when, SHA), effects with provider response ID, fallback levels, costs with source.
- Every comment and PR of the platform carries the run ID with a link into the admin UI.
- Trace: `TRACEPARENT` from event to merge; Claude Code passes `TRACEPARENT` on to subprocesses and ignores OTel variables from repo settings ([cc-monitoring] VERIFIED).
- Retention: [06](06-operations-and-deployment.md) section 5; starting values are there, the decision is made by the operator.

## 9. Threats and defenses (overview)

| Threat | Defense | Test |
|---|---|---|
| Forged events | signature before parsing; weak schemes (GitLab before 19.0, Azure DevOps) as `weak` with shared secret, IP allowlist, dedupe and fresh re-reading | S2, S6 |
| Unauthorized triggering | permissions at the provider, ticket AND repo permission, bots and forks filtered out | S2 |
| Prompt injection | separation of privileges, command covers effect, `Untrusted<T>`, sanitizer, TOCTOU, schema, agent files only from the base SHA | S1 |
| Exfiltration | egress allowlist, no secrets in the agent phase, LLM credential only in the credential relay (subscription only without a shell, except profile `operator_test` with inspection proxy), redaction with own rules for `sk-ant-*`, external links and images removed from comments | S1 |
| Third-party code on too weak isolation | repo class per claim, minimum isolation per class, pool reports verified capabilities, no fallback to a weaker level | S6 |
| Self-escalation via configuration | base SHA, `forbidden_paths` for `.agents/**` | S2 |
| Faulty config file cancels tightenings | fail closed: last valid version, otherwise at most `shadow`, `merge.mode: human`, `autonomy: low` (ADR-65) | S2 |
| Self-approve, unchecked merge | `approve` only optional for human PRs, never for agent PRs (ADR-14); `merge` only by the Effect Gateway after a deterministic merge gate at the SHA, no `propose_merge`, no bypass; `agent-approval-check` with `human`; revert PR and fallback to `human` on a red target branch | permission test against the real app, S7 |
| Third-party input controls coder and reviewer at the same time (backdoor via auto-merge) | merge gate condition 12 "provenance", attribute `foreign_input_seen`, no `auto` for `external_code` (ADR-60) | S2, S7 |
| Stale approve, withdrawal by the author | approve only under (a) to (d) from ADR-61, withdrawal of the own approve on every push | S1, permission test stage 6 |
| Agent code in the hoster's CI (secrets, open network) | agent branches like fork code, `doctor` and check per claim, otherwise `no_safe_ci` (ADR-59) | S1, S2 |
| Private content in public comments | visibility rule per source, citation check in the Effect Gateway (ADR-63) | S1 |
| Exfiltration via package names or DNS | registry cache offline from the lockfile, `propose_dependency`, DNS only in the egress proxy (ADR-64) | S1 |
| Sandbox escape on `single-host` | worker without the control plane's socket, separate networks, `doctor`; second VM recommended for `external_code` (section 1, ADR-62) | S6 |
| Workflow start in product repos | `actions:write` only in the dispatch app, which is only installed on the runner repo | permission test against the real app |
| Poisoning of KB and standards | Learnings only from humans with write permission, citation check, standards only via merged PR, KB writes only from indexer runs on the default branch | own test |
| Subscription token exfiltrated via server tools of the LLM endpoint (`operator_test`) | inspection proxy with path and body filter, otherwise profile blocked | S1 |
| Compromised worker | pool key only claim and report, revocable; tokens per item; no DB connection; results checked against the lease | S6 |
| Plugin and analyzer supply chain | trust levels, `third_party` only across a process boundary with an egress list, pinned versions, images by digest and signature check where the vendor signs, contract suite as a load condition; analyzers only in the sandbox | contract suites |
| The project's supply chain (manipulated images or dependencies) | section 10 | release gate, portability test |
| Subscription abuse | section 6 | S2 |
| Data path violated | `data_policy` when loading the configuration and during provider resolution | S2 |

## 10. Supply chain of the project

What the project itself ships must be verifiable by an operator before they start it. The reference project is the release pattern from [`bothy-vorlage-projekt-setup`](../research/bothy-vorlage-projekt-setup.md) sections 2.4, 2.7, 2.9 and 2.10 (VERIFIED there); repo setup and tools are in [12](12-open-source-and-project.md).

1. **Signed images:** every image (`control-plane`, `agent-worker`, `egress-proxy`, `sandbox-base`, amd64 and arm64) is built by digest, checked with Trivy before the tag and signed keyless with cosign. The installer, `doctor` and the Helm chart only start images whose digest is in the signed release list (hard check); they verify the cosign signature of the images if `cosign` is present, otherwise they warn with the exact verification command ([11](11-installation-and-hosting.md) section 2.4 rule 2; detailed design 06 FE-620).
2. **SBOM and attestation:** every publication carries an SBOM (Syft) and a build attestation (GitHub Artifact Attestations, for Free and Pro accounts only on public repos, VERIFIED according to the bothy research). Release jobs with signing permissions only run in an environment `release` with a required reviewer.
3. **Actions by SHA:** all actions are pinned to the full commit SHA (in addition the repo setting that enforces this); `permissions: contents: read` as the default, no `pull_request_target`, only GitHub-hosted runners on the development repo (ADR-38, [12](12-open-source-and-project.md)). Updates come via Renovate with a waiting period; a tool with a known compromised version stays pinned to the last good version.
4. **License gate:** dependencies against an allowlist, ScanCode before every release, `LICENSE`, `NOTICE` and `THIRD_PARTY_NOTICES` in every publication ([06](06-operations-and-deployment.md) section 8). Bundled analyzers and rules only with a free license (ADR-50).
5. **No proprietary software in images (ADR-39):** Claude Code, the Agent SDK and its platform packages are not in the image; no package of the project depends on the Agent SDK. The license gate checks this with a negative test: an image with the SDK package is red. The worker installs the CLI at the operator's site with a pinned version and checksum from the configuration; a deviating checksum aborts the start.
6. **Secrets in the development repo:** secret scanning with push protection and gitleaks with own rules for every Anthropic credential (`sk-ant-*`); a deny list scanner keeps operator details out of the public repo (ADR-38).
7. **Reporting path (`SECURITY.md`):** the only path is the hoster's private vulnerability reporting (GitHub Private Vulnerability Reporting), no email address. Target times for acknowledgment of receipt, assessment and fix are named values in `SECURITY.md`. Fixes appear as a security advisory with affected and fixed versions; supported are the versions according to the upgrade rule in [11](11-installation-and-hosting.md).
